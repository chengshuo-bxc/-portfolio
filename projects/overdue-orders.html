多平台发货超时订单自动提取

电商运营每天要盯「快超出承诺发货时间的订单」，逾期会扣分罚款。原来的做法是人工「订单查询 → 待发货 → 快速筛选 → 批量导出 → 等后台生成（约 5 分钟冷却）→ 下载 → 解压 → 复制订单号」，多店重复、又慢又容易漏。本工具直接调平台接口取数，多店一轮几秒钟出表，输出「合并总表 + 纯订单号清单」直接喂给内部 ERP。

拼多多 + 京东双平台 多店一轮数秒 CDP 接管已登录浏览器 PyInstaller 一键交付

项目背景

多家旗舰店的运营每天要把「发货即将超时 / 已超时」的订单捞出来，交给内部 ERP 查单处理。人工导出有 5 分钟冷却，多店反复操作极其低效，还可能漏掉跨页数据。

核心难点

平台订单接口校验请求头里的动态签名（anti-content / dsm-*），用 requests 裸调会被网关挡掉，返回的文案还伪装成「请求频繁，请2小时后重试」。硬碰硬逆向签名成本高、且平台随时改。

approach

打法：接管真浏览器，借它自己的签名

不逆向签名。用 Playwright 通过 CDP 接管用户已登录的 Chrome，监听页面自己发出的请求，把签名截下来复用；一份签名会用几次就失效，所以做成「签名池」——用一份换一份、失败重试，全程不用点页面。

core/browser_core.py · 接管已登录 Chrome 
# 启动带调试端口的 Chrome（独立配置目录保存登录态），再 CDP 接管
cmd = [chrome,
  f"--remote-debugging-port={port}", "--remote-allow-origins=*",
  f"--user-data-dir={profile_dir}", url]
subprocess.Popen(cmd, creationflags=DETACHED_PROCESS)

browser = pw.chromium.connect_over_cdp(f"http://127.0.0.1:{port}")
# ⚠ 为什么不 Playwright 自启：自启带自动化标记 navigator.webdriver=True，风控阈值更低；
#    接管真 Chrome 则原生就是 False，什么都不用遮。
core/overdue.py · 签名池 
class Signatures:
    """监听页面流量，把带 anti-content 的请求签名收进池子，一次调用花一份。"""
    def bind(self, page):
        page.on("request", self._on_req)          # 页面自己发请求 → 天然带签名
    def take(self):                               # 从新往旧取没用过的那一份
        if self._used < len(self.items):
            self._used += 1
            return self.items[len(self.items) - self._used][1]
        return None                               # 池子空了 → refill 刷新页面补货
multi-store

多店隔离：一店一账号一浏览器一端口

登录态按浏览器配置目录存，所以每家店用独立目录 + 独立调试端口，互不顶号。[逆向要点] 端口必须运行时顺序分配、启动前先清同端口残留 —— 否则会把 A 店的数据当成 B 店的（踩过）。登录后还会核对店名，对不上就跳过报警。

core/overdue.py · 防串店 
# 登录后核对当前登录店名，与配置对不上 → 跳过（最后一道防串店闸）
if cur and norm(st["name"]) not in norm(cur) and norm(cur) not in norm(st["name"]):
    log(f"[!] 登录的店是「{cur}」，与配置「{st['name']}」不一致 → 跳过")
    continue

# 收尾：CDP 的 Browser.close 才是真关浏览器
# （browser.close() 只断开连接、不关进程，会留一堆僵尸浏览器占端口）
browser.new_browser_cdp_session().send("Browser.close")
two platforms

两个平台的差异

拼多多

请求头 anti-content 动态签名；筛选参数「即将超」和「已超」的 delayShippingStatus / afterSaleType 两个都不同，照抄一个只改另一个会静默查出别的单（踩过）。pageSize 上限 20，「有没有下一页」的标志不可信。

京东

靠复用页面请求的那组头（尤其 dsm-eid），缺了返回 code=312。返回字段是嵌套的（order.predictedTime），平铺取会拿到空。店名匹配用「最长公共子串 ≥ 4」防止撞车。

delivery

交付：给运营的"双击即用"

运营电脑没有 Python、不看命令行，所以交付物是 PyInstaller onedir 打包的 exe + _internal + 一键 .bat。咬过两个硬坑：打包后 __file__ 指向 _internal（资源找不到、静默算错），以及 .bat 必须 GBK + CRLF（LF 会被 cmd 吞字符）。

体会：这个项目最值钱的不是"跑通了"，而是那些不报错的坑——端口撞了会静默拿到别人数据、__file__ 定位资源会静默算错、筛选参数抄错会静默查出别的单。AI 帮我把大段排错拆成小步，但每一步的"对不上就报错、绝不静默兜底"是我定的底线。
