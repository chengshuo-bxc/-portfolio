电商活动报名商品 ID 自动提取

大促期间运营要把「百亿补贴 / 潮流好价」报名记录里的商品 ID 全部抠出来，几百个链接、纯手工：整页复制到表格 → 删垃圾信息 → 一个个抠 ID，又慢又容易错。本工具接管已登录浏览器，模拟人工点开活动卡片、自动翻页，从接口响应里精确取 ID，几秒出一张表。

接管已登录浏览器 自动翻页 · 去重 不解析哈希类名 附接口侦察工具

项目背景

运营每天要把活动报名商品整页复制到在线表格，再删掉一堆无用信息、抠出商品 ID。几百个链接纯手工作业，容易漏、容易错，且无法复核。

核心难点

每个商品 ID 只在页面渲染里出现，页面结构用了带哈希的 CSS 类名（如 goods-info_id__2V2pq），每次平台发版都会变，写死选择器早晚崩。而接口入参虽是明文 JSON，签名仍在请求头里，裸调会被挡。

principle

原则：读页面自己发的响应，不解析会变的类名

做法是"模拟人工点「查看」→ 监听它触发的接口响应 → 从 JSON 字段取值"，而不是解析 DOM 样式。要不要点、点哪里靠稳定的业务属性（卡片上的 data-tracking-params），取值靠接口字段名 —— 这两样才是平台"改版也不会随手改"的东西。

core/scrape.py · 点动作 + 等它触发的响应 
def wait_for_api(page, action, timeout=45_000):
    """执行 action（如点「查看」），并等它触发的列表接口响应。"""
    with page.expect_response(lambda r: API_MARK in r.url, timeout=timeout) as info:
        action()
    return parse_list_response(info.value.text())   # 从 JSON 取 total / goods_items

# 卡片 = 过滤条件，用稳定的业务属性精确匹配，而不是样式类
want = f"activity_type={BAIYI_ACTIVITY_TYPE}&active_status={status}"   # 43=百亿补贴
card = page.locator(f'[data-tracking-params="{want}"]')
pitfalls

两个真实踩坑

切标签：必须点"最深"的那个元素

标签用模糊类名 [class*="TAB_card"] 匹配时，外层容器也会命中，而且它的文本里也含目标文字 → 点到容器上、标签切不动。做法是取文档顺序里最靠后的那个，点完再验证 active 状态。

调大每页条数的"竞态"

页面只给每页 10/20 条。点"每页条数"下拉项本身会触发一次列表请求——那次的响应会早到，导致后面再等响应就超时。做法是把"点下拉项"这个动作也包进"等响应"里，把它触发的数据一并吃掉。

core/scrape.py · 翻页的两道保护 
# ① 翻页没生效：本页与上页 ID 完全相同 → 判定没翻动，停（防死循环）
if new_ids == prev_ids: break
# ② 风控：错误里含"频繁" → 停手提示"等 2 小时或改天"，已采到的照常输出
if "频繁" in err: break
# 采完比对：实际采到 vs 接口自报 total，对不上显式打印差多少（不假装正常）
dev tool

配套：接口侦察脚本

字段名不能靠猜。随工程带一个侦察脚本：连上登录浏览器、把页面发出的 XHR/fetch 响应原样存盘，并打印每个接口的顶层结构、列表条数、单条字段名。[逆向要点] 平台改版时先跑它"以真实响应为准"再改取值，而不是对着报错瞎试。
