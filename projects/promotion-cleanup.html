推广链接批量管理浏览器扩展（MV3）

电商推广后台里要清理大量推广链接时，平台自带的「批量操作」只在部分标签下露出、且对某些推广类型直接禁用。运营只能一条条点「更多 → 删除 → 确定」，几百条点到手软。本扩展把这一步自动化：读取列表 → 勾选/筛选 → 先试删 1 条验证 → 批量执行，全程可停、有日志、可导出。实测 62 条连删 0 失败、约 4.9 秒/条。

Chrome MV3 扩展 模拟真人点击 · 零风控 MV3 MAIN world 注入 带离线自检

项目背景

推广投放里经常要批量删掉没效果的链接。平台自带的批量删除有限制（托管类推广一次只能删一条），而人工逐条点极慢，还容易误操作。

核心难点

后台接口校验动态签名（anti-content / Anti-Content），一份签名只能连用 3~4 次；用完继续硬冲会让风控升级，最后吐 54001 要人机验证。所以"偷签名大批量直发"这条路走不通。

key insight

关键决策：用"模拟真人点击"，而不是硬发请求

[逆向要点] 与其拿偷来的签名自己发请求（会被限速+风控加码），不如替用户在页面上点「更多 → 删除 → 确定删除」——请求由页面自己发，每次都是新鲜签名，平台看到的就是真人操作。实测后者零风控、稳定跑完。

extension/content.js · 两种模式 
// 模拟点击（默认、推荐）：替用户点行内「更多 → 删除 → 确定删除」
//  → 请求由页面自己发，每次新鲜签名，平台看到的是真人操作
async function delViaUI(row) {
  await row.more.click();                    // [data-testid="OperationsRow_More"]
  await row.menuDelete.click();              // #{opId}Dropdown 里的「删除」
  await confirmBtn.click();                  // [class*="DeleteConfirm_hack"] 里的「确定删除」
}
// 接口直发（快但易被拦，仅"一次能删一批"的场景）：由 inject.js 用偷来的签名发
//  ⚠ 一份签名只能用 3~4 次 → 硬冲会让签名寿命越缩越短 → 最后 54001
architecture

扩展架构：MAIN world 注入 + Shadow DOM 面板

inject.js（MAIN world）

页面加载前注入（document_start），hook 页面的 fetch / XHR：偷签名、克隆页面的列表请求模板（这样筛选条件永远和页面一致），并对外提供 RPC（list / del / harvest / status）。所有请求都从页面上下文发，cookie/referer/签名天然正确。

content.js（面板）

用 Shadow DOM 在右下角挂一个面板：读列表、勾选筛选、两种删除模式、进度条、实时日志、导出 Excel。与 inject.js 之间用 postMessage 做 RPC。

extension/manifest.json · MV3 
{ "content_scripts": [
  { "matches": ["…/goods/promotion/*"], "js": ["inject.js"],
    "run_at": "document_start", "world": "MAIN" },        // 抢在页面脚本前 hook
  { "matches": ["…/goods/promotion/*"], "js": ["content.js"],
    "run_at": "document_idle" } ] }
robustness

把"平台机制"变成代码里的兜底

  • 托管号一次只能删一条：平台后端对"全店托管"类推广拒批量请求 → 扩展自动改成一条条删（慢一点但删得完）。
  • 54001 自动处理：取接口返回的 verifyAuthToken → 带 VerifyAuthToken 头重试一次；再失败才让页面弹验证。
  • 错误分类：把"限速（稍后重试）"和"签名失效（请2小时后重试）"分开处理 —— 限速不能去补签名，补了也没用。
  • 换账号免重装：扩展不存账号，登录哪个号就删哪个号；换号后按 F5 刷新页面即可。
